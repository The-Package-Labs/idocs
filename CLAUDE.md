# idocs

A tool for documentation sites whose architecture diagrams are described in YAML, laid out automatically, and playable: a request can be shown travelling through the system, step by step, in several scenarios.

## Commands

```sh
pnpm install
pnpm dev               # docs site on http://localhost:4321
pnpm dev:template      # the starter project
pnpm build             # docs site to apps/docs/dist
pnpm build:packages    # compile the five packages into dist/
pnpm build:all         # packages + docs + template
pnpm test              # unit tests (vitest)
pnpm test:e2e          # builds the docs, drives them in Chrome (needs Google Chrome installed)
pnpm verify:pack       # pack, scaffold, install, build and load, like a user would (network + Chrome)
pnpm vscode:build      # the VS Code extension into extensions/vscode/dist
pnpm vscode:test       # the extension inside a real VS Code (opens a window; unset ELECTRON_RUN_AS_NODE)
pnpm vscode:package    # pack extensions/vscode into a .vsix
pnpm typecheck         # tsc everywhere (astro check does not support TypeScript 7)
pnpm lint              # biome; `pnpm format` fixes
pnpm check             # validate the example diagrams in apps/docs and templates/starter
pnpm idocs <command>   # the CLI: check, list, schema, icons search, new
pnpm changeset         # describe a change for the next release
```

Node >= 22, pnpm. `pnpm` refuses very new releases (minimum release age); if an install fails on that, loosen the range, do not disable the policy.

## Layout

```
packages/core           schema, compiler, layout, router, timeline. No UI.
  src/index.ts          browser-safe entry: types, layout, route, timeline, geometry
  src/node.ts           node-only entry: YAML parsing, Zod schema, compiler, icons, loader
packages/react          <DiagramView> and its parts, plus styles.css (all tokens are --idocs-*)
packages/astro          Astro integration (Vite plugin -> virtual:idocs/diagrams) and <Diagram>
packages/cli            `idocs`
packages/create-idocs   `npm create idocs`; carries a copy of the template, built by scripts/template.mjs
extensions/vscode       the VS Code extension (private, not on npm; own version and CHANGELOG)
  src/model, src/language   pure logic, never imports `vscode`
  src/vscode                the only code that imports `vscode`; adapters and the preview panel
  webview/                  the preview page: React + DiagramView
  syntaxes/idocs.tmLanguage.json   GENERATED by scripts/grammar.mjs
apps/docs               the tool's landing page, guides and live examples (+ e2e tests)
templates/starter       the minimal project users start from (source of truth for the template)
scripts/                build.mjs, template.mjs, verify-pack.mjs
```

Repository topology, the template repository and releasing: `docs/REPOSITORIES.md`.

## Rules that keep it working

- **`@the-package-labs/idocs-core` main entry must stay browser-safe.** No `node:*`, `yaml`, `zod`, Iconify or unified imports reachable from `src/index.ts`; they belong behind `src/node.ts`. The client bundle only gets layout, route, timeline and types.
- **The story model is pure too.** `buildStory(diagram, scenario)` in `core/src/story.ts` turns a scenario into lanes, boxes and links; `StoryView` only measures the DOM and draws connectors over it. Add behaviour to the model, with a test, not to the component.
- **Nested diagrams are linked after compiling, and levels stay mounted.** A node's `diagram:` is only a name in `CompiledNode`; `linkDiagrams` (core, pure) checks names, views, scenarios and cycles once every diagram has compiled, in `loadProject` and in the extension's `src/model/links.ts`. `attachNested` then puts the diagrams a diagram can open inside it as `nested` (flat, so nothing is carried twice): a compiled diagram is self-contained and the viewer takes no prop for it. A node can also be *expanded in place*: `layoutNested` (core) lays the inner diagram out first, bottom up as always, and gives the outer layout one larger node, so the outer layout code does not know; sizes are measured by path (`orders/api`) and `InlineDiagram` draws the result at 1:1. Cards replaced under the pointer never fire `mouseleave`, so expanding clears hover. The drawer's picture of what a node holds (`DiagramPreview`) lays out and measures that diagram itself, cached per diagram, and is static: its cards use `preview` so nothing in it can be focused. In `DiagramView` every level of the trail stays mounted and hidden, so `useLayout` must not measure while it is (a hidden container measures 0 px) and the player pauses. `CompileResult.where` is a closure, so it is non-enumerable: a worker posts `{ ...result }`.
- **The viewer is one viewport with the panel inside it, and a bar under it.** `Canvas` (the picture) and `ScrollFrame` (a sequence or a story, which scroll) are the frame; `Panel` (outline and views, nothing else) floats over its left edge, `position: absolute`, and is excluded from panning and zooming. The frame is told how much of its left edge the panel covers (`inset`): the picture is fitted and the camera centres on what is left, and `--idocs-inset` does the same for the scroller. `reserve` sizes the frame for the open panel, and `tall` keeps it so, so folding never makes the page jump. Folded, the panel is one button. Under `NARROW` (640 px) there is no room to share: the panel starts folded, and opened it is a sheet over the picture; the bar wraps into rows. The `.idocs-level` is a size container (`container: idocs / inline-size`) for that. Lists that follow the player (steps, sequence rows, story boxes) scroll their own box with `keepInView`, never the page.
- **Scenarios live on the bar, not in the panel.** `PlayerBar` sits under the frame, attached to it (`has-bar` on the workspace takes the gap back), and exists while the view has scenarios. It holds the scenario menu (`ScenarioMenu`), the words of the step (the old subtitles: `subtitles` / `defaults.subtitles` / CC now show or hide them), the transport, `StepSlider`, the `Steps` list (`StepsPopover`, reusing `StepPanel` and the phase folding) and the speed and presentation buttons. Menu and list are popovers that open upward over the picture; their height is bounded by the picture's, measured again whenever the workspace resizes. The bar keeps its height from one step to the next (two lines are reserved for the note), so the page does not jump while a scenario plays. The slider's model is pure: `buildScrubber(timeline)` (core/src/scrubber.ts) gives every step a slot of the same width (a `par` block shares one), groups slots into phase sections, and maps a moment to a place and back; the component only draws it. The panel's default is open when the diagram has another view (`hasChoices`), not when it has scenarios.
- **How a diagram opens is pure too.** `startOf(diagram, { view, scenario, mode })` (core/src/start.ts) merges what the page asked for with the diagram's `defaults:`; `Level` only reads it once. The order is the reader (hash), the page's props, the scenario's own `mode`, `defaults`, then the built-in behaviour. `defaults.sidebar` gives way in a narrow frame and the prop does not, and the hash records only departures from the opening state (`scenarioHash`, with `~` for the overview of a diagram that opens on a scenario). `openingView` (the view a nested diagram shows) honours `defaults` too.
- **The outline and the phases are pure too.** `buildOutline(diagram, view, { diagrams, expanded })` (core/src/outline.ts) is the tree: groups, nodes in authoring order, each node's drawn connections, and the nodes of a diagram shown in place under paths like `orders/stock`. `Outline` only folds rows, handles keys and calls back. Choosing a row goes through `onPick` in `Level`, which selects without toggling and glides the camera (`Focus.keep`: centre on the node, keep the zoom); `reveal` and `locate` are one-shot and clear when the scenario moves on, so following resumes. `phaseSpans(scenario)` (core/src/phases.ts) turns a scenario's phases into runs of steps. Which phases are folded is state in `Level`, per scenario, shared by the timeline, the sequence and the story; folding changes what is listed, never what plays.
- **The timeline is pure.** `buildTimeline(scenario, edgeLengths)` and `frameAt(timeline, t)` hold all playback logic; the React player is only a clock. Keep it that way: it makes scrubbing, stepping and tests trivial.
- **Never leave `will-change: transform` on the zoomed layer.** It makes the browser scale a bitmap, which blurs everything when zoomed in. `Canvas` sets it only while panning or zooming; an e2e test guards the resting state.
- **Compiled output is JSON.** `CompiledDiagram` crosses the server/client boundary as island props. No functions, classes, Maps or Dates in it.
- **Layout is group by group, bottom up** (see the comment at the top of `layout.ts`): flow groups use ELK, `rows` and `row/grid` groups are packed by us, zones are arranged by one more ELK run, and every edge ELK cannot see end to end goes through `route.ts`. Do not give ELK the whole hierarchy in one run; it forces one direction on everything.
- Heights come from the browser: `useLayout` renders cards offscreen at their fixed width, measures, then calls `layoutView`. Tests substitute fixed heights via `fakeSizes`.
- Validate in the compiler, not the renderer. A diagram that compiles must render.
- Raw HTML in markdown is dropped on purpose; compiled docs are injected with `dangerouslySetInnerHTML`.
- **In the monorepo `exports` point at TypeScript sources**; `publishConfig.exports` points at `dist/` and is applied by pnpm when packing. Do not point `exports` at `dist/`.
- **Changing the schema?** Run `pnpm idocs schema apps/docs && pnpm idocs schema templates/starter`; a test fails when the committed `diagram.schema.json` files are stale.
- **The template is generated.** Edit `templates/starter`, not a template repository. It must stay minimal and free of tool documentation. The `idocs` skill is maintained once in `skills/idocs/` (a test checks it against the code), linked from `.claude/skills/idocs` for this repo, copied into new projects, and installable by anyone with `npx skills add`.
- The five published packages are versioned together (changesets `fixed`). Add a changeset for any user-visible change.
- Dev-server gotcha: the Vite plugin loads the compiler once at startup, so restart `pnpm dev` after editing `packages/core` compile code (layout and renderer changes hot-reload).

## The VS Code extension

Details are in `extensions/vscode/DEVELOPMENT.md`. The rules:

- **`src/model` and `src/language` never import `vscode`.** They take text and positions and return plain data, so they are unit tested. Adapters live in `src/vscode`.
- **The grammar is generated.** Edit `scripts/grammar.mjs`, run `pnpm --filter idocs-vscode grammar`, commit both. Tests tokenize every diagram in the repo and compare with the `yaml` parser.
- **Do not import `@the-package-labs/idocs-core/node` in the extension.** Its icon loader uses `import.meta.url`, which a CommonJS bundle breaks on. Use `/browser` and pass icon sets (`src/model/icons.ts`).
- **`src/model/sources.ts` mirrors `loadProject`, `src/model/scaffold.ts` mirrors `idocs new`.** Tests compare each with the real thing; change the original and those tests tell you what to update.
- **Changing the format?** Completion reads the JSON schema, but steps are listed by hand in `src/language/vocabulary.ts` and a test compares them with the zod schema. The grammar's key lists (`REF_KEYS`, `KIND_KEYS`, `ENUM_KEYS`) are in `scripts/grammar.mjs`.
- **Rendering and the webview** are covered by `pnpm test:e2e` (Chrome, real content security policy); the host by `pnpm vscode:test`. Run both after touching `src/vscode`, `webview/` or `DiagramView`.
- The extension is released on its own (`vscode-v<version>` tag), not through changesets.

## The docs site and landing page

- **The landing page is not a Starlight page.** `apps/docs/src/pages/index.astro` and `src/components/landing/` own it, with their own tokens in `src/styles/landing.css` (`--lp-*`). Palettes shared with the theming guide live in `src/styles/palettes.css`. Its theme script uses Starlight's `starlight-theme` storage key so the choice carries over to the docs.
- **Docs pages are `src/content/docs/<section>/<page>.mdx`, always two levels deep**, so every cross-link is a relative `../../section/page/`. Add a page to the sidebar in `astro.config.mjs`; the sidebar is grouped by section. `e2e/links.test.ts` fails on a broken link, anchor or asset.
- **Every example on the site is a real diagram** in `apps/docs/diagrams`, so `pnpm check --strict` covers it. Write a small diagram for a new idea instead of describing it. The `tour-*` diagrams feed both the landing page and the first-diagram guide.
- **Gotchas.** A frontmatter `title` or `description` containing `: ` must be quoted. Curly braces in MDX prose need backticks. Astro's `Code` cannot load extra Shiki themes under Starlight, so `CodeWindow.astro` calls `shiki` directly. Astro does not prefix `redirects` targets with `base`, so `astro.config.mjs` does. Tests that scroll to a diagram must scroll instantly (the page uses smooth scrolling), because diagrams hydrate when visible.
- **Check what you change on a base path too**: `SITE_URL=https://x.github.io BASE_PATH=/idocs pnpm --filter idocs-docs build`.
- `apps/docs/public/og.png` is generated by `node scripts/og.mjs`.

## Style

Biome decides formatting (single quotes, no semicolons, 100 columns). Comments say why, not what. Prefer small pure functions in `core`; UI state lives in `DiagramView`.

## Testing a visual change

Unit tests cover geometry (no overlaps, edges end on borders, nothing crosses an unrelated node). For anything visual, run `pnpm dev`, open `/examples/checkout/` and `/examples/platform/`, and look at both themes. `pnpm test:e2e` covers playback, the drawer, the sequence and story views, the landing page, the docs navigation and every link in the built site.

## Authoring diagrams

Use the `idocs` skill (`skills/idocs`, linked from `.claude/skills/idocs`). Always finish with `pnpm check`.
